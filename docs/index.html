CVE-2026-55954 Critical · 9.1

ueberauth_apple — Sign in with Apple, signed but never checked

The library confirms Apple really signed the login token — and then trusts everything inside it without checking a single field: not who the token was issued for, not whether it's expired. So a borrowed or leaked Apple token logs an attacker straight in as someone else. I proved it end-to-end against the real package; fixed in 0.6.2.

CVE-2026-78922 Critical · 9.1

jsontokens — all signatures valid, when there are none

When it verifies the expanded token form, jsontokens loops over the signature array requiring every signature to check out — but never that one exists. Hand it a token carrying signature: [] and no signature at all, and verify() returns true. It bites where an app verifies the object form; I proved it against the real 4.0.1 with three negative controls.

CVE-2026-78926 Critical · 9.1

reallysimplejwt — strict to issue, wide open to verify

The library refuses to issue a token unless the secret is 12+ characters with mixed classes, then accepts a zero-length secret when it verifies one. Anyone who knows the secret is empty forges an HS256 token with any claims — the build-side policy is simply never applied on the verify path. Proven against the real 5.0.0.

CVE-2026-78929 Critical · 9.1

jose-jwt (.NET) — a zero-length key is a public key

jose-jwt never rejects a zero-length HMAC key, and an empty-key signature needs no secret to compute. When an app's HS* key resolves to an empty byte array, Jose.JWT.Decode accepts a forged token with any claims. Proven against 5.3.0 on .NET 8, with a null-key boundary control.

CVE-2026-78931 Critical · 9.1

nowakowskir/php-jwt — no key at all still verifies

The verify path recomputes the HMAC with the caller's key and never rejects a zero-length one, so JWT::validate($t, '', 'HS256') accepts an empty-key forgery. The verify algorithm is caller-forced — good anti-confusion design — but that does nothing against an empty key. Proven against 2.1.1.

CVE-2026-78924 Critical · 9.3

@sphereon/did-auth-siop — a verdict object that's always truthy

The OpenID4VP verifier delegates each presentation's signature check to a callback returning { verified }, then tests the truthiness of the object instead of its .verified field. A { verified: false } verdict counts as success, so a credential forged under an attacker key is accepted. Proven against 0.21.1.

CVE-2026-78930 High · 8.7

did-jwt-vc — the signer says attacker, the credential says victim

did-jwt-vc verifies the JWT signature against iss (correct), then lets the untrusted payload issuer override it during normalization, with no iss == issuer check. Sign with your own key while claiming a victim issuer, and any relying party that trusts the normalized issuer is deceived. Proven against 4.0.16.

This SSRF egress guard builds its denylist entirely from IPv4 CIDRs, and Ruby's IPAddr#include? never matches across address families — so every IPv6 destination walks straight past it. I proved it live against the real gem, exfiltrating a loopback-only secret.

CVE-2026-63656 Critical · 9.3

flyimg — every value escaped but one

flyimg builds an ImageMagick command line from URL options and runs it through a shell. Every value on that line is escaped except webp-method, which comes straight from the URL — so one unauthenticated GET request runs arbitrary OS commands on the image server. I proved it against the real command-builder and proc_open path; fixed in 1.12.3.
